# Allqbit — Project Status

Интерактивный сайт-«офис», продающий автоматизацию бизнес-процессов через понятные результаты:
меньше потерянных заявок, быстрее ответ клиенту, меньше рутины, понятные статусы, больше
видимости для руководства. Подробности — `CLAUDE.md` и `docs/`.

## Правила статусов

Каждый шаг имеет ровно один статус из списка: **Не приступили**, **В работе**, **Выполнено**.

Эта таблица — упрощённое зеркало `WORKPLAN.md`, где реальный прогресс хранится в 8-значном
статусном словаре (`PROPOSED / APPROVED / IN_PROGRESS / AWAITING_SKEPTIC / FAILED_REVIEW /
BLOCKED / PASSED / COMPLETED`). Источник истины — `WORKPLAN.md`; README отображает его через
mapping:

| Статус в WORKPLAN.md                               | Статус здесь  |
| -------------------------------------------------- | ------------- |
| `PROPOSED`, `APPROVED`, `BLOCKED`                  | Не приступили |
| `IN_PROGRESS`, `AWAITING_SKEPTIC`, `FAILED_REVIEW` | В работе      |
| `PASSED`, `COMPLETED`                              | Выполнено     |

В любой момент времени не более одного шага находится в статусе "В работе". Переход в
"Выполнено" происходит только после того, как пройдены все verification commands шага, получен
skeptic verdict `PASS`, и результат явно утверждён пользователем. Эта таблица обновляется в
README.md синхронно с каждым изменением статуса в `WORKPLAN.md` — одним и тем же коммитом.

## Как запустить проект

```bash
npm install
cp .env.example .env.local        # заполнить ADMIN_LOGIN, ADMIN_PASSWORD_HASH, SESSION_SECRET
npm run admin:hash-password       # получить хеш пароля администратора
npm run db:migrate                # создать/обновить базу контента
npm run db:seed                   # заполнить её текущими текстами сайта
npm run dev
```

Приложение поднимается на `http://localhost:3100` (не 3000 — порт 3000 на этой машине занят
посторонним процессом, не относящимся к проекту; см. `WORKLOG.md`, Step 1).

Требуется Node 22 или новее: база контента работает на встроенном модуле `node:sqlite`.

Прочие команды: `npm run build`, `npm run start`, `npm run lint`, `npm run typecheck`,
`npm run format:check`, `npm run test`, `npm run test:e2e`.

сайта.

## Форма «Ваша задача» → Telegram

Раздел «Ваша задача» отправляет сообщение в Telegram через серверный роут `POST /api/task`.
Пока переменные окружения не заданы, форма **честно показывает ошибку** и ничего не отправляет —
она не притворяется, что сообщение ушло.

Что нужно сделать один раз:

1. В Telegram написать [@BotFather](https://t.me/BotFather) → `/newbot` → получить **токен** вида
   `123456789:AA...`.
2. Написать своему новому боту любое сообщение (без этого он не сможет вам отвечать).
3. Узнать **chat_id**: открыть `https://api.telegram.org/bot<ТОКЕН>/getUpdates` и найти в ответе
   `"chat":{"id":...}`.
4. Создать файл `.env.local` в корне проекта по образцу `.env.example`:

   ```
   TELEGRAM_BOT_TOKEN=123456789:AA...
   TELEGRAM_CHAT_ID=123456789
   ```

5. Перезапустить `npm run dev`.

Важное:

- `.env.local` не попадает в git (см. `.gitignore`) — токен не должен оказаться в репозитории.
- **Не добавляйте префикс `NEXT_PUBLIC_`** к этим переменным: он публикует значение в браузер, и
  токен станет доступен кому угодно. Обе переменные читает только серверный код.
- При смене токена достаточно поправить `.env.local` — код трогать не нужно.

Проверить: открыть раздел «Ваша задача», отправить тестовое сообщение и убедиться, что оно пришло
в Telegram.

## Форма заявки на `/contacts` → n8n

Страница контактов отправляет заявку **только через серверный роут** `POST /api/contact`. Браузер
никогда не обращается к webhook n8n напрямую: адрес и секрет живут в серверном окружении и в
клиентский бандл не попадают.

Принимающий сценарий — **«Qbit_sait/Webhook → Telegram notification»** (тот же, что работал на
прежнем сайте): узел Webhook с методом `POST` и путём `webhook-telegram-notification`, за ним узел
Telegram, который берёт текст из `body.message`, а получателя — из `body.chat_id` с фолбэком на
chat_id владельца.

Что нужно задать в `.env.local` (образец — `.env.example`):

```
N8N_CONTACT_WEBHOOK_URL=https://<ваш-n8n>/webhook/webhook-telegram-notification
N8N_CONTACT_WEBHOOK_SECRET=<общий секрет>
```

Адрес — **production**-webhook (`/webhook/…`), а не тестовый (`/webhook-test/…`): тестовый живёт
только пока в n8n нажата кнопка «Listen for test event», и на боевом сайте отдаст ошибку. Сценарий
должен быть активен (`Active`).

Роут отправляет в n8n JSON:

```json
{
  "submissionId": "uuid, создаётся сервером",
  "source": "qbit-studio-ai-contacts",
  "page": "/contacts",
  "message": "Готовый текст заявки для Telegram",
  "name": "Павел",
  "phone": "+79370000000",
  "telegram": "@username",
  "process": "Описание задачи",
  "submittedAt": "ISO-8601 UTC",
  "attribution": {
    "yclid": "98765",
    "utm_source": "yandex",
    "utm_medium": "cpc",
    "utm_campaign": "avtomatizaciya",
    "utm_content": "obyavlenie-1",
    "utm_term": "avtomatizaciya zayavok",
    "landing_path": "/products",
    "captured_at": "ISO-8601 UTC"
  }
}
```

`page` — страница, с которой форма отправлена: `/contacts` или `/` (раздел «Ваша задача» на
главной). Значение приходит от формы и проверяется сервером по списку; неизвестное значение
становится `/contacts`. Ту же страницу называет первая строка сообщения в Telegram — «страница
«Контакты»» либо «главная страница, раздел «Ваша задача»».

`message` — то, что уходит в Telegram: текст собирает сайт (`src/features/contacts/contactMessage.ts`),
n8n остаётся транспортом. Разметка в нём не используется — узел Telegram отправлен без `parse_mode`,
и звёздочка или скобка из описания процесса иначе ломала бы сообщение. Остальные поля дублируют те
же данные по отдельности: если заявку захотят класть ещё и в таблицу или CRM, разбирать текст не
придётся.

`chat_id` сайт не передаёт намеренно — получатель настраивается в n8n, и роут не должен уметь его
переопределять.

`phone` и `telegram` приходят как `null`, если поле не заполнено (обязателен хотя бы один из двух).
Секрет уходит заголовком `X-QBit-Webhook-Secret`. Сценарий из прежнего сайта его **не проверяет** —
пока проверка не добавлена (узел IF после Webhook, сравнение
`{{ $json.headers['x-qbit-webhook-secret'] }}` с ожидаемым значением), заявку в этот webhook может
отправить кто угодно, знающий адрес.

Таймаут запроса — 9 секунд, автоматических повторов нет (повтор создал бы дубль заявки).

### Рекламный источник заявки (`attribution`)

Сайт запоминает ПОСЛЕДНИЙ рекламный переход и прикладывает его к заявке. Человек, пришедший не по
рекламе, даёт `"attribution": null` — это обычный случай, и сценарий n8n обязан его учитывать.

Как это работает:

- `src/middleware.ts` при заходе с `yclid` или любой `utm_*` кладёт метки в собственную cookie
  `qbit_attr`: `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, срок 90 дней. Заход БЕЗ меток cookie
  не меняет и не удаляет — навигация по сайту не стирает источник, за который заплачено, а новая
  рекламная ссылка его перезаписывает.
- Ответ, в котором cookie записывается, отдаётся с `Cache-Control: private, no-store` вместо
  обычного `s-maxage`: персональная метка не должна попасть в разделяемый кэш и достаться следующим
  посетителям. Остальные ответы кэшируются как раньше.
- Cookie ставится на публичных страницах; `api/`, `_next/` и пути с точкой (`favicon.ico`, картинки)
  исключены из matcher.
- `POST /api/contact` читает cookie и кладёт разобранное значение в payload. Форма источник не
  передаёт и о нём не знает.
- Сохраняются ровно восемь полей из примера выше — остальные параметры адреса (`gclid`, `fbclid`,
  `ref` и любые другие) игнорируются молча.

Все значения считаются недоверенными: их задаёт тот, кто прислал ссылку, а cookie правится в
DevTools. Поэтому и при записи, и при чтении снимаются управляющие и невидимые символы, каждое
значение режется по 200 символов, а `landing_path` приводится к внутреннему пути: абсолютный адрес
(`https://…`) заменяется на `/`, а протокол-относительный `//чужой.сайт` схлопывается до обычного
внутреннего пути `/чужой.сайт`. Правила — в `src/features/attribution/attribution.ts`.

В текст `message` атрибуция НЕ добавляется: сообщение в Telegram читает человек. Разбирать источник
должен сценарий n8n по полю `attribution`.

Записи в CRM и базу этот механизм не делает — только передача в n8n.

Пока `N8N_CONTACT_WEBHOOK_URL` не задан, роут отвечает 503, а форма показывает нейтральную ошибку и
прямые контакты — она не притворяется, что заявка ушла.

## Раздел «Кейсы» (первый этап — 2026-08-10, публикация — 2026-08-11, админ-панель — 2026-08-11)

Архив реализованных проектов: слева картотека небольших папок, справа открытое досье выбранного
кейса на фотографии рабочего стола. Дело № 01 — НАСТОЯЩИЙ кейс
(`/cases/analiz-zvonkov-otdela-prodazh`), он опубликован, и раздел индексируется. Кейсами
управляет владелец сайта из админ-панели — раздел «Кейсы» (`/admin/cases`).

- Адреса: `/cases` (обложка архива, свой H1) и `/cases/[slug]` (досье кейса). У каждого кейса
  настоящий маршрут: прямая ссылка, перезагрузка и Back/Forward работают, анимация —
  progressive enhancement.
- ИСТОЧНИК ИСТИНЫ ОДИН — таблица `cases` (миграция `0003_cases`). Кейсов в коде нет: и первое дело
  архива, перенесённое миграцией дословно, и любое созданное в админ-панели читаются одинаково
  через `src/server/content/cases.ts`. Отсюда главное свойство раздела: новый кейс не требует ни
  правки кода, ни пересборки, ни ручного добавления в карту сайта.
- Модель кейса: `src/features/cases/types.ts` (контракт отрисовки) и
  `src/features/cases/caseRecord.ts` (строка таблицы плюс её превращение в документ — единственное
  место, знающее порядок разделов и место цепочки и метрики). Репозиторий —
  `src/server/repositories/cases.ts`, API — `/api/admin/cases`.
- Разделы досье собраны из БЛОКОВ (`CaseBlock`: абзац, цепочка процесса, таблица «до/после»), а не
  из плоского списка абзацев. Порядок задаёт `caseRecordToStudy`: цепочка встаёт сразу после
  первого абзаца «Что реализовали», метрика — между первым абзацем «Результата» и оговоркой о
  применимости. Это и есть GEO-правило раздела: цифра неотделима от источника и от ограничения.
- Пользовательских ЧЕРНОВИКОВ нет. У формы создания одна конечная кнопка «Опубликовать»: кейс либо
  существует на сайте, либо не существует вовсе. Колонка `status` осталась служебной (`published`)
  — чтобы снятие кейса с публикации однажды не потребовало миграции схемы.
- Рендер раздела — `force-dynamic` (обложка, layout и досье). Запасных текстов у кейсов нет, а
  образ собирается там, где базы ещё нет: статический пререндер уехал бы в production пустым
  архивом (см. `src/tests/unit/app/rendering-mode.test.ts`). Побочное следствие полезное —
  опубликованный кейс виден на сайте сразу, а не через пять минут.
- Ссылка в конце досье — поле `cta` («Обсудить похожую задачу» → `/contacts`). Обычная ссылка в
  серверном HTML, одна на документ, без кнопок и баннеров. В форме не редактируется: это значение
  модели, одинаковое у всех дел архива, — как и служебные подписи `folderCaption` и `label`.
- Сцена, картотека и стопка листов живут в `src/app/cases/layout.tsx`: App Router размонтирует
  поддерево страницы при смене slug, и анимация, собранная внутри страницы, не пережила бы переход.
  Страница отдаёт только сам документ — весь текст кейса приходит с сервера.
- Печать: `stampEnabled` у кейса. Ставится примерно через 2 с после открытия, при
  `prefers-reduced-motion` появляется сразу и без движения. Декоративна (`alt=""`, `aria-hidden`).
- Ассеты: `npm run assets:cases` порождает адаптивные производные фона и версию печати с
  восстановленным альфа-каналом (исходник `case-stamp.png` — JPEG с нарисованной «шахматкой»
  вместо прозрачности). Исходники не изменяются.
- Индексирование ОТКРЫТО (2026-08-11): общесайтовый `INDEXABLE_ROBOTS`, canonical на обоих адресах,
  Open Graph (`og:type: article` у кейса) и Twitter — общими helper'ами `src/lib/seo.ts`. Разметка —
  `BreadcrumbList` + `WebPage` + `Organization` (`src/features/cases/casesSeo.ts`).
  `Article`/`BlogPosting` СОЗНАТЕЛЬНО нет: подтверждённой даты публикации у кейса не существует, а
  `datePublished` из даты сборки был бы выдумкой. По той же причине пусты `publishedAt`/`modifiedAt`
  и у кейса нет `lastmod` в карте сайта.
- Карта сайта берёт кейсы из того же источника (`getPublishedCases`), а не списком строк:
  опубликованный в панели кейс попадает в неё без правки `sitemap.ts`, удалённый — исчезает.
- Заголовок выдачи у кейса — поле `seoTitle`, оно берётся ДОСЛОВНО (`normalizeSeoTitle`), бренд к
  нему не дописывается; H1 документа остаётся другим и длиннее.

### Управление кейсами в админ-панели

`/admin/cases` — список дел (№ дела, название, адрес, даты публикации и изменения, порядок) с
действиями «Редактировать» и «Удалить» и кнопкой «Добавить кейс».

- Форма разбита на смысловые группы: основное, шесть разделов досье, цепочка процесса, измеримый
  результат, ограничение результата, SEO, настройки. Ни WYSIWYG, ни произвольного HTML: поля —
  обычные `textarea`, абзац отделяется пустой строкой, значения попадают в документ текстом.
- ПУБЛИКАЦИЯ. Одна конечная кнопка «Опубликовать». Сервер проверяет схему, занятость адреса и
  номера дела, записывает кейс, ставит `publishedAt` фактическим временем публикации (и то же
  значение в `modifiedAt`) и сбрасывает кэш раздела. Дальше — сообщение «Кейс опубликован» и ссылка
  «Открыть на сайте»; наружу из панели никто не перебрасывается.
- ПРАВКА. Кнопка «Сохранить изменения». `publishedAt` не меняется никогда, `modifiedAt` получает
  время правки. АДРЕС ЗАФИКСИРОВАН: в форме он показан только для чтения, а сервер берёт `slug` из
  базы и присланный игнорирует — отдельной операции переезда с перенаправлением в проекте нет.
- УДАЛЕНИЕ. Только через подтверждение с последствиями («будет удалён с сайта и из карты сайта»).
  Кнопка «Отмена» ничего не удаляет. После удаления адрес отвечает 404, строка исчезает из
  картотеки и карты сайта; автоматических перенаправлений не создаётся. Предыдущая версия текста
  уходит в `content_revisions`.
- Дата публикации перенесённого дела № 01 осталась ПУСТОЙ: подтверждённой даты у него нет, а дата
  миграции рассказывала бы о базе, а не о проекте.
- Приёмка: `src/tests/e2e/cases-admin.spec.ts` (проходит весь путь публикация → правка → удаление
  в браузере). Спека требует ОТДЕЛЬНОГО тестового администратора — `E2E_ADMIN_LOGIN` и
  `E2E_ADMIN_PASSWORD`; без них она пропускается, настоящий пароль владельца сайта ей не нужен.
