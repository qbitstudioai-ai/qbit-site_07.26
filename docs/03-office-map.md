# Office Map

## Предварительное расположение

```text
┌──────────────────────────────────────────────────────────────┐
│                  ДИРЕКЦИЯ / УПРАВЛЕНИЕ                       │
│                                                              │
│  ТЕХНИЧЕСКАЯ ПОДДЕРЖКА      ОБЩАЯ ЗОНА             HR        │
│                                                              │
│       ПРОДАЖИ                            ЛОГИСТИКА            │
└──────────────────────────────────────────────────────────────┘
```

## Логика

- Дирекция находится выше и принимает агрегированные потоки.
- Поддержка — крупная операционная зона слева.
- Продажи — заметная нижняя левая зона.
- HR связан с переговорными и зоной ожидания.
- Логистика — операционная правая нижняя зона с картами и статусами.
- Центр объединяет офис и резервирует место для hero.

**Правка 2026-07-16 (см. `docs/05-homepage-state-machine.md` "overview", правка той же даты):** эта
строка описывала расположение зон, пока hero оставался виден одновременно с офисом (состояние
`overview`, решение Step 3/4/5). Пользователь решил это пересмотреть — после раскрытия офиса
(`overview`) hero полностью скрывается, место под него больше не резервируется: офис занимает весь
экран. Формулировка выше остаётся верной только для состояния `hero` (до раскрытия), не для
`overview`.

## Каждая зона имеет

- стабильный `departmentId`;
- HTML-кнопку;
- SVG/DOM-контур;
- hover/focus/selected;
- доступную подпись;
- короткое описание проблемы.

## Камера

Нет свободного полёта. Только:

- слабый параллакс;
- контролируемое приближение;
- переход в 10/90;
- короткое переключение;
- однозначный возврат.

## Режим 10/90

Левая панель 10–14%:

- возврат;
- пять миниатюр;
- активное состояние;
- клавиатурная навигация.

Основная область:

- сцена;
- заголовок;
- симптомы;
- до/после;
- результат;
- CTA.

**Правка 2026-07-16 (пользователь сверил визуал department-active с планом; правки той же даты в
`docs/05` "overview" и новый `WORKPLAN.md` Step 7.2 про hero):** формулировки выше — устаревшее
решение Steps 3/5/6, пересмотрены пользователем целиком для состояния `department-active`. Новая
структура экрана (без hero, без подсказки — см. `docs/05` "overview" правку той же даты) слева
направо:

1. **Левая панель** — не только текстовые названия ("пять миниатюр" уже подразумевало картинки,
   формулировка не менялась): у каждого из 5 отделов теперь и название, и собственное фото. Позади
   панели — общее фото офиса (то же, что фон `overview`), которое становится темнее/бледнее, когда
   отдел открыт (не полностью скрывается, тот же принцип "офис остаётся контекстом", что уже
   действует для `overview`).
2. **Основная область — не одна колонка, а две**, примерно 20/80:
   - **20% (левая, "боль")** — ровно **5** пунктов конкретных проблем ("что можно
     автоматизировать", с акцентом на боль отдела) — кликабельны/фокусируемы.
   - **80% (правая, "выгода")** — при выборе конкретного пункта боли показывает **именно её**
     выгоду (что получит бизнес, решив ЭТУ конкретную проблему: деньги/время/ресурсы) — не общий
     список результатов отдела, а связка "один к одному" с выбранной болью.
3. Сцена (`DepartmentScene`), последовательность "до/после" (`BeforeAfterSequence`) — по-прежнему
   не входят в текущий low-fidelity milestone (см. `WORKPLAN.md` Step 6 Out of scope, OQ-C); заголовок
   и CTA остаются как раньше.

**Последствие для контента:** переход с "3 симптома + 5 несвязанных результатов" (`docs/12`
"максимум три симптома", `data/departments.json`) на "ровно 5 пар боль→выгода" — реальное изменение
модели данных, не только вёрстки. Требует правки `docs/12-content-data-model.md`, схемы
(`src/content/schema.ts`), `content/types.ts` и содержимого `data/departments.json` для всех 5
отделов. Реализация — новый шаг `WORKPLAN.md` "Step 7.3 — Department view redesign (pain/gain
panel)"; на момент этой правки не начата. Точный текст всех 25 пар (5 отделов × 5 пар) будет
написан/скорректирован отдельно (пользователь: "текст можешь написать, но потом будем править") — см.
черновой пример для "Дирекция" в `WORKPLAN.md` Step 7.3.

## Mobile

Не уменьшенная карта, а отдельный touch-путь: обзор, карусель/пейджинг карточек отделов (одна
карточка видна за раз, переключение кнопками «предыдущий»/«следующий»), полноэкранная карточка
открытого отдела с прямым переключением между отделами, явная кнопка назад и CTA.

**Правка 2026-07-16 (планирование Step 7 "Mobile touch flow", решение пользователя по OQ-M5):**
формулировка выше буквально описывала "список отделов" без карусели/пейджинга и без прямого
переключения между уже открытыми отделами — расхождение с `docs/08-responsive-behavior.md`
("список/карусель отделов", расплывчато) было найдено при skeptic Phase A review плана Step 7,
после того как пользователь уже выбрал карусельный вариант (OQ-M3). Пользователь подтвердил
карусель как осознанное решение и явно попросил честно поправить этот документ под фактическое
намерение, а не откатывать уже выбранную архитектуру — по тому же прецеденту, что уже дважды
применялся к `docs/05-homepage-state-machine.md` (Step 3/Step 5, "honesty-правка после skeptic
FAIL"). Реализация — Step 7 (`WORKPLAN.md`), ещё не начата на момент этой правки.
