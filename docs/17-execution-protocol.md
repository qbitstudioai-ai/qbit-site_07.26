# Strict Execution Protocol

## Назначение

Этот протокол регулирует работу основной сессии Claude Code, planner-агента, агента-скептика и специализированных ревьюеров.

Цель — исключить ситуацию, когда Claude:

- начинает разработку без утверждённого плана;
- объединяет несколько шагов;
- сам оценивает собственную работу;
- меняет архитектуру по ходу выполнения;
- переходит дальше при непроверенном результате;
- заявляет о выполнении проверок без фактического запуска.

## Роли

### Основная сессия Claude Code

Выполняет роль координатора и исполнителя:

- собирает контекст;
- вызывает planner;
- вызывает skeptic;
- согласует план с пользователем;
- выполняет один шаг;
- запускает проверки;
- ведёт `WORKPLAN.md` и `WORKLOG.md`;
- не выносит окончательный вердикт по собственному шагу.

### Planner

Только анализирует и планирует.

Planner:

- читает документацию;
- изучает код;
- определяет зависимости;
- разбивает работу на минимальные проверяемые шаги;
- задаёт критерии приёмки;
- задаёт команды проверки;
- определяет риск и rollback;
- не редактирует production-код.

### Skeptic

Независимый read-only ревьюер.

Skeptic:

- не доверяет отчёту исполнителя без проверки;
- сравнивает план и фактический diff;
- ищет пропущенные требования;
- проверяет тестовые доказательства;
- ищет регрессии;
- оценивает архитектуру, доступность и производительность;
- возвращает только `PASS`, `FAIL` или `BLOCKED`;
- не исправляет код.

### Специализированные ревьюеры

- `frontend-architect` — архитектура и качество frontend;
- `qa-reviewer` — независимая приёмка;
- `ux-strategist` — пользовательский путь;
- `motion-engineer` — motion и производительность.

Они вызываются после этапов и при профильных изменениях.

## Жизненный цикл задачи

```text
USER REQUEST
    ↓
PLANNER DRAFT
    ↓
SKEPTIC PLAN REVIEW
    ↓
PLAN CORRECTION
    ↓
USER APPROVAL
    ↓
STEP 1 EXECUTION
    ↓
LOCAL CHECKS
    ↓
SKEPTIC STEP REVIEW
    ├── FAIL → FIX → CHECKS → SKEPTIC
    ├── BLOCKED → PLAN AMENDMENT → USER APPROVAL
    └── PASS → STEP 2
    ↓
MILESTONE REVIEW
    ↓
NEXT MILESTONE
```

## Правило одного шага

Один шаг должен:

- иметь один основной результат;
- занимать ограниченный scope;
- проверяться отдельными критериями;
- иметь понятный diff;
- допускать откат;
- не смешивать инфраструктуру, новую функцию и визуальный polish без необходимости.

Плохой шаг:

> Создать весь интерактивный офис, сделать мобильную версию, анимацию и тесты.

Хорошие шаги:

1. Создать typed data model отделов.
2. Создать semantic overview с пятью кнопками.
3. Реализовать state machine overview/preview.
4. Реализовать выбор отдела.
5. Реализовать 10/90 shell.
6. Реализовать keyboard и focus return.
7. Реализовать mobile presentation.
8. Добавить reduced motion.
9. Добавить Playwright flows.

## Обязательные файлы

### `WORKPLAN.md`

Содержит утверждённый план, статусы и критерии.

### `WORKLOG.md`

Содержит доказательства исполнения:

- время;
- шаг;
- изменённые файлы;
- команды;
- результаты;
- ошибки;
- skeptic verdict;
- исправления;
- остаточные риски.

### `DECISIONS.md`

Содержит решения, изменяющие архитектуру или scope.

## Skeptic gate

Следующий шаг запрещён, пока текущий не получил `PASS`.

Self-review исполнителя не считается skeptic review.

Устное сообщение:

> Всё выглядит правильно.

не является доказательством.

Допустимое доказательство:

- diff просмотрен;
- команды перечислены;
- exit codes известны;
- сценарий воспроизведён;
- требования сопоставлены;
- verdict записан.

## Плановые изменения

После утверждения план нельзя менять молча.

Amendment должен содержать:

- причину;
- старый scope;
- новый scope;
- влияние;
- новые риски;
- изменённые критерии;
- мнение skeptic;
- решение пользователя.

## Когда можно не запускать полный цикл

Только для:

- исправления опечатки;
- изменения одного текста без влияния на layout;
- комментария;
- документации без продуктового решения.

Даже в этом случае нужно показать diff и проверить форматирование, если оно настроено.

## Момент остановки

Claude должен остановиться и запросить решение, когда:

- требования противоречат друг другу;
- нужен секрет или внешний доступ;
- меняется утверждённая архитектура;
- тест не может быть запущен;
- skeptic возвращает `BLOCKED`;
- исправление выходит за scope;
- требуется неподтверждённое бизнес-решение.
