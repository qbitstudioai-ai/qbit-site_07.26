## 1. Как выполнялся аудит

### Встроенный `/security-review` запустить в этом репозитории не удалось

Skill присутствует (`security-review — Complete a security review of the pending changes on the
current branch`), но его первая же команда — `git diff origin/HEAD...` — падает:

```
fatal: ambiguous argument 'origin/HEAD...': unknown revision or path not in the working tree
```

Причина: у репозитория **нет ни одного remote** (`git remote -v` пуст) и единственная ветка
`master`. Базы `origin/HEAD` не существует.

Что было предпринято, по порядку:

1. Проверена версия Claude Code — 2.1.172.
2. Загружен официальный файл Anthropic
   `anthropics/claude-code-security-review` → `.claude/commands/security-review.md`. Он оказался
   **той же самой diff-ориентированной командой** (`git diff --merge-base origin/HEAD`), то есть
   имеет ровно то же ограничение. Замена его копией проблему не решала.
3. Попытка дать команде корректную базу: создан временный ref `refs/remotes/origin/HEAD` на коммит
   пустого дерева. Не сработало — `origin/HEAD...HEAD: no merge base` (истории не связаны).
   **Временный ref немедленно удалён**, состояние git восстановлено.
4. Итог: в `.claude/commands/security-review.md` записан проектный вариант команды — критерии и
   формат вывода взяты из официального файла Anthropic, а область проверки заменена с diff на
   **весь рабочий каталог**. Это соответствует и требованию задачи («нельзя ограничиваться текущим
   diff»).

Встроенный skill перекрывает одноимённую проектную команду по имени, поэтому регламент из этого
файла исполнялся напрямую двумя независимыми аудиторами (зона 1 — авторизация/API/БД, зона 2 —
XSS/файлы/заголовки/секреты), каждый из которых читал `.claude/commands/security-review.md` как
инструкцию. Результаты затем перепроверены вручную на живом production-сервере.

> **Вывод, который важен для повторяемости:** `/security-review` в текущем виде непригоден для
> аудита всего репозитория без remote. После публикации проекта на удалённый репозиторий штатный
> skill заработает и его следует использовать для проверки будущих изменений.

## 2. Модель угроз

| Актор | Возможности | Что защищаем |
| --- | --- | --- |
| Аноним из интернета | HTTP-запросы к любому публичному маршруту | Недопустить: вход в админ-панель, чтение файлов сервера, чтение неопубликованного контента, порчу контента, отказ в обслуживании |
| Аноним с известной ссылкой на файл | GET к `/api/files/*` | Файлы снятых с публикации документов |

| Владелец сайта (единственный админ) | Полный доступ к панели | Не является атакующим; но введённый им текст не должен превращаться в код для посетителей |
| Сеть между посетителем и сервером | Пассивное чтение, активная подмена при HTTP | Перехват сессии, downgrade TLS |

Вне модели: физический доступ к серверу, компрометация Node/ОС, злонамеренный владелец сайта.

### Два дефекта, внесённых самими исправлениями и найденных на ревью

Оба обнаружены независимой проверкой уже после первой волны правок и устранены. Фиксирую их
открыто — исправление, которое само создаёт проблему, обязано попадать в отчёт.

| Что | Как проявлялось | Устранено |
| --- | --- | --- |
| Общий счётчик попыток входа применялся и к известному адресу | Давало дешёвый и **бессрочный** lockout владельца: порог достигается ~7 запросами в минуту, заблокированные запросы новых записей не создают, снять блокировку из интерфейса нечем. То есть защита от перебора менялась на отказ в обслуживании | Счётчики разведены и применяются взаимоисключающе (`isLoginBlocked`): известный адрес → только свой лимит, неизвестный → только общий. Покрыто тестом «поток чужих неудачных попыток не блокирует вход с другого адреса» |
| Базовая CSP из `next.config.ts` перекрывала собственную политику роута `/api/files` | Заголовки из `headers()` вытесняют одноимённые, выставленные роутом. `sandbox; default-src 'none'` пропадал — а именно он лишает загруженный файл прав на исполнение и делает безопасным отсутствие проверки сигнатуры. Проверено запросом к реальному файлу: политика `sandbox` на месте, на главной — базовая, файл отдаётся целиком |

## 5. Ложные срабатывания — рассмотрены и отклонены

| Кандидат | Почему это не уязвимость |
| --- | --- |
| Path traversal в `/api/files/[...path]` | `resolveStoragePath` отбрасывает NUL-байт, затем сравнивает **нормализованный** `path.resolve()` с корнем по префиксу `root + path.sep`. `..`, абсолютные пути и `\` нормализуются ДО проверки. Второй независимый рубеж: расширение обязано быть в белом списке, куда `.env`, `.db`, `.ts` не входят. Подтверждено live-запросами выше |
| Отсутствие проверки сигнатуры файла (magic bytes) при загрузке | Решение принимается по расширению, но выдача обезврежена: `Content-Type` берётся из серверного белого списка (не из файла), стоит `X-Content-Type-Options: nosniff` и `Content-Security-Policy: sandbox; default-src 'none'`. HTML, переименованный в `.txt`, отдаётся как `text/plain`; в `.png` — не декодируется. Полиглот не попадает в исполняемый контекст. Полезное усиление, но пути эксплуатации сегодня нет |
| Инъекция заголовка через `?name=` в `Content-Disposition` | Значение сначала лишается `"`, `\`, CR, LF, затем проходит `encodeURIComponent` внутри `filename*=UTF-8''…`. Процентное кодирование делает CR/LF инертными |
| SVG среди отдаваемых типов | SVG **нельзя загрузить** (его нет в `ALLOWED_UPLOAD_TYPES`). Отдаются только предпросмотры, которые сервер строит сам по фиксированному шаблону, пропуская внешние значения через `escapeXml`. Плюс та же sandbox-политика |
| `zip` в белом списке загрузки | Отдаётся как `application/zip` с `nosniff` и sandbox; браузер не исполняет содержимое архива. Загрузить может только владелец сайта |
| Clickjacking `/admin` (до добавления заголовков) | Cookie `SameSite=Lax` не прикрепляется к кросс-сайтовой загрузке во фрейме — враждебная страница получала бы неавторизованный запрос и редирект на `/login`. Накладывать было не на что. `frame-ancestors`/`X-Frame-Options` всё равно добавлены |
| SQL-инъекции | Проверены все семь репозиториев и `auth/*`. Каждый пользовательский параметр идёт через `?`. Шаблонные литералы содержат только статические константы, объявленные в том же модуле. `ORDER BY` везде зашит жёстко; сортировки по полю из запроса нет |
| Prototype pollution через слияние `page_content` | `JSON.parse` создаёт `__proto__` как СОБСТВЕННОЕ свойство, spread копирует через CopyDataProperties — сеттер прототипа не вызывается. Уязвимый `Object.assign`/рекурсивный merge в коде отсутствует |
| Open redirect через `?next=` | Закрыт дважды: middleware ставит параметр только при `target.startsWith("/admin")`, страница входа независимо перепроверяет то же условие. `//evil.com` и абсолютные URL не проходят |
| Утечка неопубликованного через `/api/content/[section]` | Фильтрация в SQL (`status = 'published'`, `is_published = 1`). Маппер `toDocumentItem` намеренно выбрасывает `storageKey`, `autoPreviewKey`, `manualPreviewKey` |
| Session fixation | Пред-аутентификационной сессии не существует; cookie выдаётся только после успешной проверки пароля; идентификатор — свежие `randomBytes(32)` (256 бит); клиент не может навязать свой ID (HMAC проверяется `timingSafeEqual`) |
| Разные ответы/тайминг при неверном логине и неверном пароле | `safeCompare` и `verifyPassword` вызываются ОБА до ветвления; ответ, статус и текст идентичны |
| `secure: NODE_ENV === "production"` | Корректно: в production флаг ставится, в dev его отсутствие необходимо для `http://localhost` |
| Middleware проверяет только подпись cookie, а не действительность сессии | Сознательный двухрубежный дизайн: на Edge нет базы. Настоящую проверку делают `admin/layout.tsx` и `requireSession()` в каждом роуте. Cookie удалённой сессии проходит middleware, но получает 401/redirect дальше |
| Middleware не покрывал `/api/admin/*` (до правки) | Не эксплуатировалось: каждый admin-роут независимо проверяет сессию — проверено построчно по всем 11 роутам. Единственное исключение по форме, но не по существу: `/api/admin/logout` вызывает не `requireSession()`, а `getActiveSessionId()` — без действующей сессии он просто ничего не делает. Худшее, чего добивается посторонний, — принудительный выход уже вошедшего владельца, и это дополнительно закрыто проверкой Origin (SEC-06) |
| `npm audit`: 12 high | См. `TECHNICAL_AUDIT.md` §«Зависимости». Реального пути эксплуатации в этом проекте нет ни у одной из трёх групп |

## 7. Рекомендации для production

Полный список с чекбоксами — в `PRE_RELEASE_CHECKLIST.md`. Самое существенное:

1. **`TRUST_PROXY=1` обязателен** — и только вместе с nginx, который **перезаписывает**
   `X-Forwarded-For`: `proxy_set_header X-Forwarded-For $remote_addr;`. Конфигурация с
   `$proxy_add_x_forwarded_for` тоже работает (код берёт последний элемент), но перезапись строже.
   Без reverse proxy `TRUST_PROXY` ставить **нельзя** — иначе SEC-02 открывается заново.
2. Приложение не должно быть доступно из интернета напрямую: слушать `127.0.0.1:3100`, наружу —
   только nginx на 443.
3. HTTPS обязателен: без него cookie сессии не получит флаг `Secure`, а HSTS не действует.
4. `var/content.db` и `var/uploads/` — на постоянном диске, вне каталога развёртывания; обновление
   приложения не должно их затрагивать.
5. Резервная копия обязана включать **и базу, и uploads** — по отдельности они бесполезны.
6. Ограничение размера запроса на nginx: `client_max_body_size 25m` (совпадает с `MAX_UPLOAD_BYTES`).
7. `.env` — права `600`, владелец — пользователь сервиса, вне git.
