# Админ-панель Allqbit

Панель управления содержимым сайта: тексты пяти отделов, десять продуктов и общие тексты страницы
«Продукт и стоимость», статьи блога, контакты и документы. Вход — по ссылке **«Вход»** в шапке
сайта (`/login`).

Главное правило: **любое сохранённое и опубликованное изменение появляется на сайте без пересборки
проекта и без правки исходного кода.**

---

## 1. Архитектура

```
Браузер
  │
  ├─ Публичные страницы (Server Components)
  │     └─ src/server/content/*      ← чтение опубликованного контента
  │
  ├─ /login → POST /api/admin/login  ← создаёт серверную сессию (cookie HttpOnly)
  │
  └─ /admin/* (Server Components + клиентские формы)
        └─ /api/admin/*              ← проверка сессии → валидация Zod → репозиторий → revalidate
                                           │
                                           ├─ SQLite   (var/content.db)   — тексты и записи
                                           └─ Файлы    (var/uploads/)     — документы и предпросмотры
```

Слои и где они лежат:

| Слой             | Расположение               | Задача                                                           |
| ---------------- | -------------------------- | ---------------------------------------------------------------- |
| База и миграции  | `src/server/db/`           | соединение, прогон миграций                                      |
| Репозитории      | `src/server/repositories/` | чтение и запись сущностей, история изменений                     |
| Публичное чтение | `src/server/content/`      | `getDepartments()`, `getProducts()`, `getPublishedArticles()`, … |
| Авторизация      | `src/server/auth/`         | пароль, сессии, ограничение попыток входа                        |
| Хранилище файлов | `src/server/storage/`      | загрузка, удаление, предпросмотры                                |
| Правила API      | `src/server/api/`          | проверка сессии, схемы Zod, сброс кэша                           |
| Интерфейс панели | `src/features/admin/`      | каркас, формы, редакторы разделов                                |

Публичные компоненты об админ-панели не знают: они получают готовые данные пропсами от серверных
страниц. Поэтому переход на другое хранилище (например, Postgres) сводится к замене репозиториев —
ни одна страница сайта не меняется.

## 2. База данных

**SQLite** через встроенный модуль Node `node:sqlite`. Файл — `var/content.db`.

Почему так: постоянное хранилище без внешнего сервиса, без нативной сборки и без дополнительных
зависимостей; Node 22+ содержит драйвер в стандартной библиотеке. База лежит файлом вне `src/` и
`public/`, поэтому переживает пересборку и деплой при условии, что директория смонтирована томом.

Таблицы:

| Таблица               | Что хранит                                                         |
| --------------------- | ------------------------------------------------------------------ |
| `departments`         | пять отделов: системный id, название, JSON-содержимое, публикация  |
| `products`            | десять продуктов: id, slug, названия, JSON контента/раскладки/зоны |
| `page_content`        | общие тексты страниц по ключу (`homepage`, `products`, `blog`, …)  |
| `articles`            | статьи: slug, тексты, Markdown, раздел, рубрика, статус, даты, SEO |
| `contacts`            | телефоны, почта, мессенджеры — единый источник для всего сайта     |
| `documents`           | документы: метаданные, ключи файлов в хранилище, предпросмотры     |
| `document_categories` | справочник категорий документов (стабильные ключи)                 |
| `content_revisions`   | предыдущая версия записи перед каждой перезаписью                  |
| `activity_log`        | журнал действий для главной страницы панели                        |
| `admin_sessions`      | активные сессии администратора                                     |
| `login_attempts`      | неудачные попытки входа (ограничение частоты)                      |
| `schema_migrations`   | применённые миграции                                               |

Схема описана в `src/server/db/schema.mjs`. Файл на JavaScript намеренно: его читают и приложение,
и скрипты `db:migrate`/`db:seed`, которые запускаются обычным `node` без сборщика — одна копия
схемы вместо двух расходящихся.

## 3. Файловое хранилище

Загруженные файлы лежат в `var/uploads/`:

```
var/uploads/documents/<uuid>.<расширение>   — оригиналы документов
var/uploads/previews/<uuid>.<расширение>    — изображения предпросмотра
```

Файлы НЕ лежат в `public/`: содержимое меняется во время работы сервера, а `public/` в production
не перечитывается. Раздачей занимается роут `/api/files/[...path]`, который:

- не выпускает запрос за пределы `var/uploads` (пути с `..` отбрасываются);
- отдаёт `Content-Type` строго из белого списка, а не из имени файла;
- ставит `X-Content-Type-Options: nosniff` и `Content-Security-Policy: sandbox; default-src 'none'`;
- по `?download=1` отдаёт файл вложением, а не открывает в браузере.

## 4. Переменные окружения

Полный список с пояснениями — в `.env.example`. Скопируйте его в `.env.local`.

Обязательные:

| Переменная            | Назначение                                               |
| --------------------- | -------------------------------------------------------- |
| `ADMIN_LOGIN`         | логин единственного администратора                       |
| `ADMIN_PASSWORD_HASH` | хеш пароля целиком, вместе с префиксом `scrypt:`         |
| `SESSION_SECRET`      | случайная строка ≥ 32 символов для подписи cookie сессии |

Необязательные (есть значения по умолчанию):

| Переменная         | По умолчанию                 |
| ------------------ | ---------------------------- |
| `QBIT_DATA_DIR`    | `./var`                      |
| `QBIT_DB_PATH`     | `<QBIT_DATA_DIR>/content.db` |
| `QBIT_UPLOADS_DIR` | `<QBIT_DATA_DIR>/uploads`    |

Ни одной из них нельзя давать префикс `NEXT_PUBLIC_` — он публикует значение в клиентский бандл.
Логин, хеш пароля и секрет сессии читаются только серверным кодом и в браузер не попадают.

## 5. Как создать хеш пароля

```bash
npm run admin:hash-password
```

Скрипт запросит пароль скрытым вводом (эхо выключено), попросит повторить и напечатает строку вида
`ADMIN_PASSWORD_HASH=scrypt:16384:8:1:...`. Сам пароль нигде не сохраняется и в вывод не попадает.

Части хеша разделены двоеточием, а не долларом, как в канонической записи scrypt. Причина
практическая: Next.js раскрывает `$переменные` внутри `.env`-файлов, в том числе в кавычках, и
`scrypt$16384$8$1$…` молча превратился бы в мусор. Отказ выглядел бы как «Неверный логин или
пароль» без единой подсказки, что дело в файле окружения. Хеши старого формата продолжают
приниматься на чтение.

Для неинтерактивной среды пароль можно передать переменной `ADMIN_PASSWORD`:

```bash
ADMIN_PASSWORD='ваш-пароль' npm run admin:hash-password
```

Секрет сессии:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"
```

## 6. Миграции

```bash
npm run db:migrate
```

Приложение применяет миграции само при первом обращении к базе, поэтому отдельный запуск нужен
там, где схему обновляют до старта сервера: деплой, новая машина, CI.

Новая миграция добавляется элементом в массив `migrations` в `src/server/db/schema.mjs`.
Существующую миграцию править нельзя — на уже развёрнутой базе изменённый текст повторно не
выполнится.

## 7. Seed

```bash
npm run db:seed              # добавляет только отсутствующие записи
npm run db:seed -- --reset   # очищает контентные таблицы и заполняет заново
```

Источник — `data/departments.json`, `data/homepage-copy.json` и `data/seed/*.json`. Это те же
тексты, что были в исходном коде до появления админ-панели, перенесённые дословно.

Скрипт идемпотентен: существующие записи не трогаются, поэтому повторный запуск не затирает правки
владельца сайта. Файлы документов копируются в объектное хранилище, а не остаются ссылками на
`public/` — удаление документа из панели должно удалять и сам файл.

## 8. Запуск

```bash
npm install
cp .env.example .env.local        # заполнить ADMIN_LOGIN, ADMIN_PASSWORD_HASH, SESSION_SECRET
npm run admin:hash-password       # получить хеш и вписать его в .env.local
npm run db:migrate
npm run db:seed
npm run dev                       # http://localhost:3100
```

Production:

```bash
npm run build
npm run start                     # http://localhost:3100
```

## 9. Как войти

1. Открыть сайт и нажать **«Вход»** в шапке (или перейти на `/login`).
2. Ввести логин и пароль, заданные переменными окружения.
3. После успешного входа открывается `/admin`.

Сессия живёт 8 часов, хранится строкой в базе и cookie `HttpOnly` + `SameSite=Lax` (в production
ещё и `Secure`). Кнопка **«Выйти»** удаляет строку сессии — вернуть доступ копией cookie нельзя.

При неверных данных ответ одинаков для неверного логина и неверного пароля. После 10 неудачных
попыток с одного адреса вход блокируется на 15 минут.

## 10. Как добавить статью

1. **Блог → Создать статью.**
2. Заполнить название, адрес (slug), краткий анонс.
3. Выбрать **раздел сайта** из списка и рубрику. Свободного ввода раздела нет намеренно: статья с
   выдуманным разделом не появилась бы нигде.
4. Написать текст в Markdown. Кнопка **«Показать предпросмотр»** отрисовывает его тем же
   разборщиком, что и публичная страница.
5. Статус **«Черновик»** — статья сохраняется, но на сайте не видна. Статус **«Опубликована»** —
   появляется в списке блога, открывается по своему адресу и попадает в `sitemap.xml`.
6. **Сохранить** (или `Ctrl+S`).

Адрес статьи уникален: занятый slug даёт понятную ошибку формы, а не ошибку сервера.

Разметка статьи:

- заголовок раздела — строка вида `**Название раздела:**`;
- списки — `-` и `1.`;
- жирный `**текст**`, курсив `*текст*`, код в тройных апострофах;
- ссылки `[текст](адрес)`.

Произвольный HTML и `<script>` не выполняются: текст разбирается и отрисовывается как React-разметка,
строка Markdown никогда не подставляется в страницу как HTML.

## 11. Как добавить документ

1. **Документы → Добавить документ.**
2. Название, описание, категория (из справочника), дата, порядок.
3. Выбрать файл. При необходимости — изображение предпросмотра.
4. **Загрузить документ.**

При загрузке сервер проверяет расширение и размер, кладёт файл под сгенерированным именем, создаёт
предпросмотр (см. ниже) и только потом создаёт запись. Опубликованный документ сразу появляется на
`/documents` в нужной ячейке — правки компонентов не требуется.

## 12. Как создаётся предпросмотр

| Формат                                    | Предпросмотр                                                |
| ----------------------------------------- | ----------------------------------------------------------- |
| JPG, JPEG, PNG, WebP                      | сам файл — отдельная копия не создаётся                     |
| TXT, CSV                                  | лист с первыми строками текста, генерируется сервером в SVG |
| PDF                                       | автоматически **не создаётся** — загружается вручную        |
| DOC, DOCX, XLS, XLSX, PPT, PPTX, RTF, ZIP | автоматически **не создаётся** — загружается вручную        |

Для PDF нужна серверная растеризация первой страницы (pdfium / poppler / ghostscript); такого
модуля в проекте нет, а `sharp` PDF не читает. Вместо имитации сделан честный резервный сценарий:
администратор загружает изображение предпросмотра вручную, а без него на публичной странице
показывается аккуратная заглушка формата. Место под серверную генерацию оставлено — схема уже
различает автоматический и ручной предпросмотр.

В форме документа можно: увидеть текущий предпросмотр, заменить его вручную, удалить ручной (тогда
возвращается автоматический, если он есть).

## 13. Поддерживаемые форматы

Загрузка документа: `pdf`, `doc`, `docx`, `xls`, `xlsx`, `ppt`, `pptx`, `txt`, `csv`, `rtf`, `zip`,
`jpg`, `jpeg`, `png`, `webp`. Максимальный размер — 25 МБ.

Изображение предпросмотра: `jpg`, `jpeg`, `png`, `webp`.

Список — «белый»: неизвестный формат запрещён по умолчанию. Исполняемые файлы и SVG загружать
нельзя: SVG исполняется браузером как код, а безопасной санитизации SVG в проекте нет.

Настраивается в `src/server/config.ts` (`ALLOWED_UPLOAD_TYPES`, `MAX_UPLOAD_BYTES`).

## 14. Резервная копия

Всё состояние — две сущности: файл базы и директория загрузок.

```bash
# копия
cp var/content.db  backup/content-$(date +%F).db
cp -r var/uploads  backup/uploads-$(date +%F)

# восстановление
cp backup/content-2026-07-27.db var/content.db
cp -r backup/uploads-2026-07-27/* var/uploads/
```

Сервер при копировании лучше останавливать. Копию базы «на живую» корректнее снимать средствами
SQLite:

```bash
node -e "const {DatabaseSync}=require('node:sqlite'); const db=new DatabaseSync('var/content.db'); db.exec(\"VACUUM INTO 'backup/content.db'\"); db.close()"
```

Отдельно: `content_revisions` хранит по 20 последних версий каждой записи — случайно затёртый текст
можно достать оттуда JSON-ом, не поднимая всю резервную копию.

## 15. Развёртывание в production

**Действующая процедура — в `DEPLOY.md`.** Сайт работает в Docker-контейнере на сервере, где уже
живёт Supabase, и обновляется командой `./deploy.sh`. Список ниже описывает те же требования в
общем виде — он полезен, чтобы понимать, откуда взялись шаги в `DEPLOY.md`, но выполнять руками
его не нужно.

1. Задать `ADMIN_LOGIN`, `ADMIN_PASSWORD_HASH`, `SESSION_SECRET` в окружении сервера (не в
   репозитории).
2. Смонтировать постоянный том и указать на него `QBIT_DATA_DIR` — иначе база и файлы будут
   теряться при каждом деплое.
3. `npm ci && npm run build`.
4. `npm run db:migrate` (при первом развёртывании — ещё и `npm run db:seed`).
5. `npm run start`.
6. Обязательно HTTPS: cookie сессии в production выдаётся с флагом `Secure` и по http не сохранится.
7. Директорию `var/` не отдавать веб-сервером напрямую — файлы раздаёт только `/api/files/*`.

Требование к среде: Node 22 или новее (нужен встроенный модуль `node:sqlite`). Проверено на Node 24.

При горизонтальном масштабировании SQLite-файл должен быть один и доступен всем экземплярам, либо
репозитории переводятся на сетевую БД — это заменяемый слой.

| Раздел               | Что можно менять                                                                                                                                                                                          |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Отделы               | название, подпись в офисе, проблема в обзоре, описание при наведении, заголовок, «что происходит сейчас», 5 пар «проблема → результат», 4 пункта выгоды, текст кнопки, публикация                         |
| Продукты и стоимость | общие тексты страницы, подписи вкладок и разделов, форматы внедрения, SEO; по каждому продукту — названия, адрес, описание, где применяется, примеры, тарифы, примечание, выгода, порядок, показ на сайте |
| Блог                 | создание, правка, копия, публикация, снятие с публикации, удаление, порядок, раздел, рубрика, обложка, SEO                                                                                                |
| Контакты             | телефон, почта, Telegram и другие каналы (единый источник для шапки и страницы контактов), тексты страницы                                                                                                |
| Документы            | загрузка, метаданные, категория, предпросмотр, порядок, публикация, удаление вместе с файлами                                                                                                             |

## Ограничения

- Продукты нельзя удалять: все десять связаны с фотографиями лаборатории и зонами на них. Чтобы
  убрать продукт с сайта, есть переключатель «Показывать на сайте».
- Отделов ровно пять, у каждого ровно 5 пар «проблема → результат» и 4 пункта выгоды: столько мест
  предусмотрено раскладкой экрана.
- Системные идентификаторы отделов (`sales`, `support`, `executive`, `hr`, `logistics`) и продуктов
  (`product-01`…`product-10`) не редактируются.
- Раздел размещения статей сейчас один — «Блог». Новый добавляется строкой в
  `src/content/article-placements.ts` и страницей, которая вызывает `getPublishedArticles(placement)`.
- Предпросмотр PDF и офисных форматов не создаётся автоматически (см. п. 12).
- Администратор один; ролей и регистрации нет.
