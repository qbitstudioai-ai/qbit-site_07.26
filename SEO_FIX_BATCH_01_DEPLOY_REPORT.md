## 1. Исправление линта

Ошибка `react-hooks/set-state-in-effect` в `src/features/how-we-work/HowWeWorkPage.tsx`
существовала до этой работы и блокировала quality gate. Устранена **причина**, а не симптом:
правило не отключалось, `eslint-disable` не добавлялся, конфигурация ESLint не менялась.

**Было.** Эффект ступенчатого появления акцента начинался с трёх синхронных `setState`: при
`prefers-reduced-motion` помечал акцент готовым, иначе сбрасывал два состояния в `null`. Готовность
хранилась как «номер готовой сцены» и сравнивалась с `activeIndex`. Каждый синхронный `setState` в
теле эффекта — лишний каскадный рендер.

**Стало.**

- Индекс сцены и номер её включения объединены в одно состояние `scene = { index, activation }`;
  `activation` строго возрастает при каждом переходе. Одно состояние, а не два соседних: иначе
  индекс и номер включения разъехались бы на один рендер и появление акцента моргнуло бы.
- Введён `revealToken` = `${scene.activation}:${reduced|full}`.
- Готовность выводится: `isAccentReady = prefersReducedMotion || accentReadyToken === revealToken`.
- Эффект только заводит и чистит таймеры; при reduced motion сразу `return`.

**Почему токен, а не просто снятие сброса.** `SCENE_TRANSITION_LOCK` = 1120 мс короче
`ACCENT_REVEAL_DELAY` = 1500 мс, поэтому есть окно ~380 мс, в котором можно уйти в соседнюю сцену
и вернуться ДО срабатывания таймера. При наивном сравнении по номеру сцены старое значение совпало
бы с текущим индексом, и акцент показался бы мгновенно вместо повторного проигрывания. Возрастающий
`activation` делает такое совпадение невозможным.

**Отличие на один кадр, зафиксированное честно.** При `prefers-reduced-motion` прежний код на один
рендер после смены сцены давал «акцент не готов», новый — сразу «готов». Это устранение
однокадрового мигания в режиме, который обязан показывать всё мгновенно. Формально поведение
отличается, поэтому записано явно, а не отнесено к «ничего не изменилось».

**Долг, не внесённый этой правкой.** `startTransitionLock` по-прежнему вызывается внутри updater'а
`setScene` — приём предсуществующий, правилом линта не покрыт. Записан в `WORKLOG.md`.

## 6. Изменение Caddy

### Правка

```diff
-allqbit.ru, www.allqbit.ru {
+allqbit.ru {
 	encode gzip zstd
 	reverse_proxy allqbit-site:3000
 	header -Server
 }
+
+www.allqbit.ru {
+	redir https://allqbit.ru{uri} permanent
+	header -Server
+}
```

### Две вещи, которые едва не сорвали применение

**1. `caddy validate` для этой конфигурации нерабочий.** Проверка падает с ошибкой
`http_basic: base64-decoding password: illegal base64 data` — но это не следствие правки: **точно
та же ошибка возникает на текущем работающем конфиге**, что было проверено отдельно. Причина —
пароль basic-auth Supabase хранится открытым, а хеш вычисляется на старте контейнера. Вместо
непригодного `validate` использован `caddy adapt`: он проверяет синтаксис без provisioning модулей.
Оба файла адаптировались с exit 0, а сравнение полученного JSON показало, что изменились ровно
хосты (`['allqbit.ru','www.allqbit.ru']` → два отдельных блока), а `supabase.allqbit.ru` не тронут.

**2. Обычный `caddy reload` сломал бы basic-auth Supabase.** Контейнер запускается командой
`PROXY_AUTH_PASSWORD=$(caddy hash-password …) && caddy run …`, то есть у работающего процесса
пароль **захеширован**, а `docker exec` получает исходный открытый. Reload из exec подставил бы в
конфиг нехешированное значение. Решение — воспроизвести логику entrypoint:

```bash
docker exec supabase-caddy sh -c \
  'PROXY_AUTH_PASSWORD=$(caddy hash-password --plaintext "$PROXY_AUTH_PASSWORD") \
   caddy reload --config /etc/caddy/Caddyfile --adapter caddyfile'
```

Перед применением этот механизм проверен **холостым reload неизменённого конфига** — безопасная
проба: exit 0, сайт 200, Supabase Studio 401 (basic-auth провизионился корректно).

### Применение

`reload`, не `restart`. Контейнер `supabase-caddy` продолжает работать с 2026-06-29,
`RestartCount = 0` — простоя не было ни у сайта, ни у Supabase.

### Соседние сервисы на общем прокси

`supabase.allqbit.ru` — **401** (`WWW-Authenticate: Basic realm="restricted"`), `/rest/v1/` —
**401**, `supabase-caddy` — `Up 4 weeks`, перезапусков нет.

**Отдельно про подлинность basic-auth.** Анонимный 401 возвращается и при рабочем пароле, и при
испорченном, поэтому по нему одному судить нельзя. Проверено иначе — чтением работающей
конфигурации через админ-API Caddy (само значение не выводилось):

```text
пользователь задан: True | длина хеша: 60 | префикс: $2a$ | валидный bcrypt: True
```

В применённом конфиге лежит **корректный bcrypt-хеш**, а не открытая строка: значит reload
подставил именно хешированное значение. Исходный текст пароля при этом тот же самый — и entrypoint
контейнера, и команда reload читают одну и ту же переменную окружения контейнера; entrypoint
переопределял её только внутри своего процесса, поэтому `docker exec` видит ровно ту строку,
которую хешировали при старте. Разные соли дают разные хеши одного пароля — вход не меняется.

Косвенное подтверждение того же: редирект в production работает, а он появился только вместе с
новым конфигом. Конфиг, не прошедший provisioning, в Caddy не подменяет работающий — reload
атомарен. Значит новая конфигурация провизионирована целиком, включая basic-auth.

## 9. Остающиеся риски и долги

- Резервные копии лежат на том же сервере, выгрузка наружу не настроена (предупреждает сам
  `backup.sh`). Существующий риск проекта.
- Порядок наложения на `/how-we-work` держится на трёх значениях `z-index` без автотеста.
- Нижняя граница 120 символов у description — свойство текущих текстов, не гарантия кода.
- Тело 404 блога не отрисовывается на сервере: статус и `noindex` корректны, но без JavaScript
  страница пуста. Поведение Next.js 16 при `notFound()` из компонента маршрута, предсуществующее.
- `/products/<неизвестный-slug>` отдаёт встроенную англоязычную заглушку Next.js.
- `updated_at` ни разу не правленной записи равен моменту `db:seed`.
- `startTransitionLock` вызывается внутри updater'а `setScene` — линтом не покрыто.
