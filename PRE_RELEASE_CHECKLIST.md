# Предрелизный чеклист Allqbit → allqbit.ru

Составлен по итогам аудита 2026-07-27. Основания: `SECURITY_AUDIT.md`, `TECHNICAL_AUDIT.md`.

Разделы идут по убыванию обязательности. Пункты «обязательно» — условия, без которых вердикт
аудита «готов к размещению» **не действует**.

---

## A. Обязательно до публикации

### A1. Инфраструктура сервера

- [ ] **Node.js 22 или новее** (проект использует встроенный `node:sqlite`; проверено на 24.13.0).
- [ ] Приложение слушает **только localhost**: `next start -p 3100 -H 127.0.0.1`. Прямой доступ из
      интернета к порту приложения закрыт.
- [ ] **Reverse proxy (nginx) перед приложением.** Без него не работает ни HTTPS, ни защита от
      перебора пароля в полном виде.
- [ ] **HTTPS с валидным сертификатом** для `allqbit.ru` (Let's Encrypt). Без HTTPS cookie сессии
      не получает флаг `Secure`, а `Strict-Transport-Security` не действует.
- [ ] Редирект `http://` → `https://` на уровне nginx.
- [ ] Firewall: наружу открыты только 80 и 443. Порт 3100 закрыт.

### A2. Переменные окружения

- [ ] `ADMIN_LOGIN` — задан.
- [ ] `ADMIN_PASSWORD_HASH` — получен через `npm run admin:hash-password`. **Открытый пароль нигде
      не хранится.**
- [ ] `SESSION_SECRET` — случайный, **не короче 32 символов** (код требует минимум 16, `.env.example`
      рекомендует 32; берём строгую границу). Получить:
      `node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"`.
- [ ] **`TRUST_PROXY=1`** — ставится **только вместе с nginx** из A1. Без reverse proxy эту
      переменную задавать **нельзя**: она снова откроет обход ограничения попыток входа (SEC-02).
- [ ] `QBIT_DATA_DIR` (или `QBIT_DB_PATH` + `QBIT_UPLOADS_DIR`) — указывают на **постоянный диск
      вне каталога развёртывания**.
- [ ] `N8N_CONTACT_WEBHOOK_URL`, `N8N_CONTACT_WEBHOOK_SECRET` — если используется форма контактов.
- [ ] `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` — если используется форма «Ваша задача».
- [ ] Ни одна из переменных выше **не имеет префикса** `NEXT_PUBLIC_`, `VITE_` или `PUBLIC_`.
- [ ] Файл `.env` — права `600`, владелец = пользователь сервиса, вне git.

### A3. Конфигурация nginx

- [ ] `proxy_set_header X-Forwarded-For $remote_addr;` — **перезапись, а не дописывание**. Вариант
      `$proxy_add_x_forwarded_for` тоже допустим (код берёт последний элемент цепочки), но
      перезапись строже.
- [ ] `proxy_set_header Host $host;` — иначе сломается проверка Origin для админ-API.
- [ ] `proxy_set_header X-Forwarded-Proto $scheme;`
- [ ] `client_max_body_size 25m;` — совпадает с `MAX_UPLOAD_BYTES` приложения.
- [ ] Ограничение частоты на уровне nginx для `/api/admin/login`, `/api/contact`, `/api/task`
      (`limit_req_zone`) — чтобы поток не доходил до Node.

Ориентир:

```nginx
limit_req_zone $binary_remote_addr zone=qbit_login:10m rate=10r/m;

server {
    listen 443 ssl http2;
    server_name allqbit.ru;

    client_max_body_size 25m;

    location /api/admin/login {
        limit_req zone=qbit_login burst=5 nodelay;
        proxy_pass http://127.0.0.1:3100;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location / {
        proxy_pass http://127.0.0.1:3100;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

### A4. Данные и права

- [ ] `var/content.db` — владелец = пользователь сервиса, права `600`.
- [ ] `var/uploads/` — владелец = пользователь сервиса, права `700`.
- [ ] Каталог `var/` **не находится** внутри каталога, который перезаписывается при обновлении.
- [ ] Проверено: `var/` не отдаётся веб-сервером напрямую (обращение к `/var/content.db` → 404).
- [ ] `npm run db:seed --reset` **не входит** в процедуру развёртывания (флаг очищает контентные
      таблицы).

### A5. Автозапуск и восстановление

- [ ] systemd-юнит с `Restart=always`.
- [ ] Автостарт при загрузке сервера (`systemctl enable`).
- [ ] Проверено вручную: после `kill -9` процесс поднимается сам.
- [ ] Проверено вручную: после перезагрузки сервера сайт доступен, **а контент, введённый через
      админ-панель, на месте**.

### A6. Резервное копирование

- [ ] Ежедневная копия включает **и `var/content.db`, и `var/uploads/`**. По отдельности они
      бесполезны: база ссылается на файлы, файлы без базы не отображаются.
- [ ] Копия базы снимается корректно для SQLite в WAL-режиме: `sqlite3 content.db ".backup ..."`
      или остановка сервиса на время копирования. **Простой `cp` работающей базы может дать
      непоследовательный снимок.**
- [ ] Копии хранятся вне этого сервера.
- [ ] **Восстановление проверено на практике** — не только создание копии, но и разворачивание её
      на чистом окружении.

### A7. Функциональная приёмка (ручная, в чистом профиле браузера)

Публичная часть — открыть и убедиться, что страница отрисована и в консоли нет ошибок сайта
(ошибки вида `chrome-extension://…` не считаются):

- [ ] Главная, все 5 отделов, все 10 продуктов, стоимость.
- [ ] Блог: список и отдельная статья.
- [ ] Контакты, документы, скачивание документа.
- [ ] 404 на несуществующем адресе.
- [ ] Прямые ссылки на вложенные маршруты и **обновление страницы** на них (F5).

Админ-панель:

- [ ] Неверный логин → «Неверный логин или пароль».
- [ ] Неверный пароль → **тот же самый текст и тот же статус**.
- [ ] Успешный вход.
- [ ] Прямое обращение к `/admin` без сессии → редирект на `/login`.
- [ ] Выход → повторное открытие `/admin` снова требует входа.
- [ ] Редактирование каждого типа контента: отделы, продукты, контакты, статьи, документы.
- [ ] Публикация и снятие с публикации статьи.
- [ ] Загрузка документа, изменение порядка, удаление.
- [ ] Два параллельных административных запроса (например, сохранение в двух вкладках).

### A8. Актуализация контента без пересборки

**Не проверено в ходе аудита — обязательно пройти вживую.** По каждому пункту: изменить в панели →
обновить публичную страницу → проверить **в новом окне браузера** → проверить **после перезапуска
сервера**:

- [ ] Каждый из 5 отделов.
- [ ] Общие тексты продуктов и каждый из 10 продуктов.
- [ ] Контакты (проверить, что обновился и телефон в шапке — он рендерится layout'ом).
- [ ] Создание, редактирование, публикация, снятие с публикации, удаление статьи.
- [ ] Загрузка, публикация, изменение порядка, удаление документа.

### A9. Проверка заголовков на живом домене

- [ ] `curl -sSD - -o /dev/null https://allqbit.ru/` содержит `Content-Security-Policy`,
      `Strict-Transport-Security`, `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options`,
      `Permissions-Policy`.
- [ ] `X-Powered-By` **отсутствует**.
- [ ] `https://allqbit.ru/admin` без сессии → редирект на `/login`, заголовок
      `Cache-Control: no-store`.
- [ ] `https://allqbit.ru/robots.txt` содержит `Disallow: /api/`.
- [ ] Обращение к `https://allqbit.ru/api/files/../../.env` → 404.
- [ ] `https://allqbit.ru/api/files/documents/<любой>` отдаёт
      `Content-Security-Policy: sandbox; default-src 'none'` — **именно эта политика**, а не общая.
      Она лишает загруженный файл прав на исполнение; при правке `headers()` в `next.config.ts` её
      легко перекрыть базовой (такая регрессия уже возникала в ходе аудита).
- [ ] **Проверить `Cache-Control` на главной.** На локальной production-сборке `/` отдаёт
      `private, no-cache, no-store, max-age=0, must-revalidate`, хотя `build` помечает страницу как
      статическую. Приложение таких заголовков для `/` не ставит (`no-store` в конфиге — только для
      `/admin`, `/api/admin`, `/login`), источник не выяснен. Если это сохранится на боевом сервере,
      статика фактически не кэшируется, и обоснование «мгновенный первый экран», которым оправдан
      отказ от строгой nonce-CSP, теряет силу — тогда стоит вернуться к строгой CSP.

## D. Что невозможно проверить до размещения на реальном сервере

Фиксируется явно, чтобы это не выглядело проверенным:

- Действие HTTPS, `Strict-Transport-Security` и флага `Secure` на cookie — требуют настоящего TLS.
- Поведение за reverse proxy: корректность `Host`, `X-Forwarded-For` и, как следствие, работа
  ограничения попыток входа и проверки Origin в production-конфигурации.
- Права доступа к `var/content.db` и `var/uploads` на боевой ОС.
- Автозапуск, перезапуск после сбоя, ротация логов.
- Реальное восстановление из резервной копии.
- Сохранность данных при обновлении приложения.
- Поведение при конкурентной записи из нескольких процессов и при повреждении файла базы
  (разрушительные тесты на единственной пользовательской базе намеренно не проводились).
