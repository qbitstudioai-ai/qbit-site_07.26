# Мобильные дефекты — аудит 2026-07-28

Реестр находок мобильной и планшетной приёмки. Полный отчёт — `MOBILE_AUDIT.md`, покрытие по
адресам — `MOBILE_ROUTE_MATRIX.md`.

Уровни: **Blocker** — основная функция недоступна; **High** — существенная часть страницы
недоступна; **Medium** — заметная проблема удобства; **Low** — небольшая визуальная или техническая
проблема.

Все измерения выполнены Playwright/Chromium на production-сборке. Поведение реального Safari на
iPhone эмуляцией не доказывается — см. `MOBILE_PRE_RELEASE_CHECKLIST.md`.

## Исправлено

### MOB-01 — High — точки маршрута «Как мы работаем» невозможно нажать пальцем

| Поле       | Значение                                                                                                            |
| ---------- | ------------------------------------------------------------------------------------------------------------------- |
| Маршрут    | `/how-we-work`                                                                                                      |
| Viewport   | 320×568, 360×640, 375×667, 390×844, 667×375, 844×390, 932×430, 768×1024, 820×1180, 1024×768, 1180×820 — то есть все |
| Устройство | любое с касанием (`pointer: coarse`)                                                                                |
| Статус     | **Исправлено**                                                                                                      |

**Воспроизведение.** Открыть `/how-we-work` на телефоне. Справа — колонка из пяти точек, каждая
соответствует локации («Миссия и ценности», «Анализ», «Внедрение», «Почему Qbit», «Письмо»).
Попытаться перейти к конкретной локации нажатием на её точку.

**Ожидаемое.** Область попадания не меньше 44×44 px; нажатие открывает именно выбранную локацию.

**Фактическое.** Кнопки имели размер 8×8 px при шаге 20 px между центрами. Замерено:
`{"w":8,"h":8}` на всех перечисленных экранах. Контактное пятно пальца шире всей колонки, поэтому
выбор конкретной из пяти локаций был случайным.

**Смягчающее обстоятельство (проверено, не отменяет дефект).** Последовательный обход свайпом
работал: `HowWeWorkPage.tsx` слушает `touchstart`/`touchend` с порогом 54 px. Недоступным был именно
ПРЯМОЙ переход — единственный способ вернуться к уже просмотренной локации, не пролистывая
остальные. Поэтому уровень High, а не Blocker.

**Причина.** `.office-route-dots button { width: 8px; height: 8px }` в
`src/features/how-we-work/HowWeWorkPage.module.css`; отдельной области попадания для касания
не предусматривалось.

**Исправление.** Блок `@media (pointer: coarse)` в том же файле: кнопка становится прозрачной
мишенью 44×44, видимая точка (те же 8 px, та же рамка, фон и свечение) переезжает в `::before`,
`gap: 0` удерживает шаг между центрами ровно 44 px, `right: 16px` компенсирует возросшую ширину
колонки. Оптический центр точки остался на прежнем расстоянии от края кадра — замерено 38 px до и
после на всех проверенных ширинах. Условие `pointer: coarse`, а не ширина экрана: дело в способе
ввода. Desktop с мышью правило не видит.

**Тест.** `src/tests/e2e/mobile-audit-regressions.spec.ts` → «MOB-01 how-we-work: точки маршрута
доступны пальцем» (11 экранов) и «MOB-01 how-we-work: desktop-вид точек не изменился» (4 экрана,
проверяет сохранение 8×8).

### MOB-02 — High — мобильное меню не помещается в экран в альбомной ориентации

| Поле       | Значение                                                  |
| ---------- | --------------------------------------------------------- |
| Маршрут    | все страницы (общая шапка)                                |
| Viewport   | 568×320, 667×375, 844×390 и любой экран высотой < ~450 px |
| Устройство | телефон в альбомной ориентации                            |
| Статус     | **Исправлено**                                            |

**Воспроизведение.** Повернуть телефон горизонтально, открыть любую страницу, нажать кнопку меню.

**Ожидаемое.** Меню помещается в экран целиком либо прокручивается; все восемь пунктов достижимы.

**Фактическое.** Замерено на 667×375: панель меню занимает `y: 64 … 441` при высоте экрана 375 px.
Пункты «Контакты» и «Вход» находятся ниже края экрана. Прокрутить список нечем: `max-height` не
задан, `overflow-y` наследует `visible`, `scrollHeight === clientHeight`. Два пункта меню
не существовали для пользователя, повернувшего телефон.

**Причина.** В `@media (max-width: 900px)` у `.navigation` (`Header.module.css`) заданы позиция и
оформление раскрытой панели, но не ограничение по высоте.

**Исправление.** `.navigationOpen` получил `max-height: calc(100dvh - 72px)` (с `100vh` как запасным
вариантом для браузеров без `dvh`), `overflow-y: auto` и `overscroll-behavior: contain`. 72 px = 64 px
фактической высоты шапки на этом брейкпоинте + 8 px воздуха. `dvh` обязателен: в мобильном Safari
`vh` завышен на высоту адресной строки.

**Тест.** «MOB-02 мобильное меню помещается в экран» — 8 экранов; проверяет и нижнюю границу панели,
и достижимость каждого пункта прокруткой.

### MOB-03 — Medium — раскрытое меню не закрывается мимо, не блокирует фон и не удерживает фокус

| Поле       | Значение                   |
| ---------- | -------------------------- |
| Маршрут    | все страницы (общая шапка) |
| Viewport   | все ≤ 900 px               |
| Устройство | телефон, планшет           |
| Статус     | **Исправлено**             |

**Воспроизведение.**

1. Открыть меню, нажать в любом месте страницы мимо меню.
2. Открыть меню, дойти Tab до последнего пункта и нажать Tab ещё раз.

**Ожидаемое.** (1) Меню закрывается, фон не принимает случайное нажатие. (2) Фокус остаётся внутри
раскрытого меню.

**Фактическое.** (1) `aria-expanded` оставался `true`, а нажатие уходило прямо в страницу — можно
было открыть отдел или перейти по ссылке, не заметив, что меню раскрыто. (2) Фокус уходил на
содержимое страницы под накладкой; клавиатурный пользователь терял и меню, и место в документе.

**Причина.** Подложки не существовало; управление фокусом ограничивалось обработкой Escape.

**Исправление.** `Header.tsx`: подложка (`data-menu-backdrop`, `position: fixed`,
`touch-action: none`), закрывающая меню и возвращающая фокус на кнопку; ловушка фокуса на Tab и
Shift+Tab, замкнутая на паре «кнопка меню → пункты». Подложка скрыта от дерева доступности
(`aria-hidden` + `tabIndex={-1}`): она не добавляет возможностей (Escape и кнопка меню уже
закрывают), а объявленная стала бы вторым элементом с подписью «Закрыть меню».

**Отдельно:** высота подложки задана явно (`calc(100dvh - 64px)`), а не выведена из `inset`. У
`<button>` при `height: auto` размер считается по содержимому даже когда заданы и `top`, и
`bottom` — первая редакция правки дала подложку 667×0, и нажатие мимо меню в неё не попадало.
Поймано собственной проверкой до фиксации результата.

**Тест.** «MOB-03 мобильное меню: закрытие и фокус» (4 сценария) и «MOB-03 desktop: подложки и
кнопки меню нет» (4 экрана).

### MOB-04 — Medium — мелкие мишени в разделе продуктов при вводе пальцем

| Поле       | Значение                                                                                    |
| ---------- | ------------------------------------------------------------------------------------------- |
| Маршрут    | `/products/*`                                                                               |
| Viewport   | 932×430, 844×390 (телефон в альбомной ориентации — ширина > 767 px, ввод остаётся касанием) |
| Устройство | телефон, планшет                                                                            |
| Статус     | **Исправлено**                                                                              |

**Фактическое.** Пункты списка продуктов — 36 px по высоте вместо заявленных в CSS 40
(`.productNav` — flex-колонка с `flex: 1`, при нехватке высоты пункты сжимались). Хлебные крошки —
14 px.

**Исправление.** `@media (pointer: coarse)` в `ProductsExperience.module.css`: `min-height: 44px` и
`flex-shrink: 0` для пунктов (список уже имеет `overflow-y: auto`, поэтому экран не переполняется);
для крошек — прозрачная область попадания через `::after` (`inset-block: -15px`), а не отступы:
отступы сдвинули бы заголовок продукта, то есть меняли бы вёрстку ради размера мишени.

**Тест.** «MOB-04 продукты: мишени при вводе пальцем» и «MOB-04 продукты: desktop не изменился»
(проверяет сохранение `min-height: 40px` и отсутствие накладки).

### MOB-06 — Medium — оговорка о расчётном эффекте не читается на телефоне

| Поле       | Значение                          |
| ---------- | --------------------------------- |
| Маршрут    | `/` (hero, информационная панель) |
| Viewport   | ≤ 1199 px и ≤ 520 px              |
| Устройство | телефон, планшет                  |
| Статус     | **Исправлено**                    |

**Фактическое.** «Расчётный эффект для руководителя», «Расчётный потенциал на основе данных CRM» и

**Исправление.** `0.72rem` (11.5 px) в обоих мобильных media query `HeroInfoPanel.module.css`.
Правило `@media (max-height: 720px) and (min-width: 1200px)` — desktop — не тронуто.

**Тест.** «MOB-06 главная: оговорка о расчёте читаема на телефоне» (4 экрана).

## Найдено, НЕ исправлено — требует решения владельца

Ни одна из этих находок не блокирует использование сайта. Каждая требует продуктового или
дизайнерского решения, то есть выходит за рамки «исправить мобильную версию, не выполняя
самостоятельный редизайн».

### MOB-07 — Low — текст локации обрезается на мобильном без способа раскрыть

| Поле     | Значение                                                               |
| -------- | ---------------------------------------------------------------------- |
| Маршрут  | `/how-we-work`, сцены 0–2 («Миссия и ценности», «Анализ», «Внедрение») |
| Viewport | ≤ 860 px                                                               |
| Статус   | **Не исправлено**                                                      |

Описание локации ограничено тремя строками: `-webkit-line-clamp: 3` + `overflow: hidden`
(`HowWeWorkPage.module.css`, `@media (max-width: 860px)`). Способа раскрыть остаток нет. Сцены 3 и 4
это ограничение явно отменяют — то есть решение принималось осознанно и по сценам.

Не исправлено потому, что снятие ограничения меняет мобильную композицию сцены: панель занимает
`max-height: 38vh` над фотографией, и полный текст либо перекроет ключевой объект кадра, либо
потребует новой раскладки. Это дизайнерское решение, а не исправление дефекта.

**Варианты:** (а) оставить как есть; (б) снять ограничение на всех сценах, как уже сделано для 3 и 4;
(в) добавить раскрытие по нажатию.

### MOB-08 — Low — декоративная панель уменьшается через `transform: scale()`

| Поле     | Значение          |
| -------- | ----------------- |
| Маршрут  | `/how-we-work`    |
| Viewport | ≤ 860 px          |
| Статус   | **Не исправлено** |

`.office-overview-dashboard` использует `transform: scale(0.82)` / `scale(0.94)`. Чек-лист приёмки
(§8) прямо не рекомендует масштабирование интерфейса. Здесь оно применено к декоративной панели, а
не ко всему экрану, и текст внутри неё не является единственным носителем смысла. Переход на
собственные мобильные размеры — работа по вёрстке этой панели, отдельным решением.

### MOB-09 — Low — предпросмотр цены продукта доступен только по наведению

| Поле     | Значение                                        |
| -------- | ----------------------------------------------- |
| Маршрут  | `/products` (обзорная сцена)                    |
| Viewport | > 767 px с касанием: 844×390, 932×430, планшеты |
| Статус   | **Не исправлено**                               |

`.markerDetails` раскрывается по `:hover` / `:focus-visible`. На ≤767 px этот блок намеренно скрыт
от экрана и заменён отдельным мобильным предпросмотром цены (`.mobilePricePreview`), но на телефоне
в альбомной ориентации ширина превышает 767 px, работает desktop-ветка, а наведения нет.

Информация при этом не теряется: нажатие по метке открывает страницу продукта, где цена и состав
показаны полностью, а клавиатурный `:focus-visible` предпросмотр раскрывает. Требование §19
(«для каждого действия существует touch-альтернатива») выполнено — действие доступно тапом.
Недоступен именно предварительный показ.

**Вариант исправления:** распространить мобильную ветку на `pointer: coarse` независимо от ширины.
Это заметно меняет вид обзорной сцены на планшетах, поэтому вынесено на решение владельца.
